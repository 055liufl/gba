# apps/

CLI applications for GBA. Currently contains a single binary crate: `gba-cli`.

## Key files

- **gba-cli/src/main.rs** — Entry point: Ctrl+C handler, CLI parsing, error formatting with colored output
- **gba-cli/src/cli.rs** — Clap derive definitions: subcommands (`init`, `plan`, `run`, `list`) and global flags (`--model`, `--budget`, `--verbose`)
- **gba-cli/src/commands/** — Command handlers that bridge CLI args to core engines (`InitEngine`, `PlanEngine`, `RunEngine`)
- **gba-cli/src/tui/** — ratatui-based terminal UI for the `plan` command: `app.rs` (state machine), `ui.rs` (rendering), `event.rs` (crossterm events)

## Patterns

- Each command module follows the same pattern: build `GbaContext` → construct engine → call `engine.run()` → display results
- TUI uses a state machine (`Input`, `Waiting`, `Done`) with async message passing between the plan engine and the UI event loop
- Error display in `main.rs` formats `anyhow` error chains with red `error:` prefix and indented cause chain
- The binary is named `gba` (configured in `Cargo.toml` via `[[bin]]`)

## Dependencies

- Depends on `gba-core` (engines, types, state) and `gba-pm` (prompt manager for the plan TUI)
- Uses `clap` for argument parsing, `ratatui`/`crossterm` for TUI, `tracing-subscriber` for log output

## Gotchas

- The `plan` command uses TUI by default; stdin/stdout fallback is not implemented — terminal must support raw mode
- CLI flag overrides (`--model`, `--budget`) are applied via `GbaContext::apply_overrides()` after config loading
- Integration tests for CLI parsing live in `tests/cli_parsing.rs`, not in the source modules
